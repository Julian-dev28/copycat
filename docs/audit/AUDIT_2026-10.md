# copycat audit, 2026-10

Read-only audit. Baseline: HEAD `0d8ac77` plus the uncommitted WIP in the tree at audit time (another
session was editing `services/hl/hl/env.py`, `venue.py`, `services/mcp/*` and the web shell during the audit;
none of those edits touch the findings below unless noted). Gate suite: `1223 passed, 19 deselected` (12.7 s).
`services/web/src/lib/api/schema.gen.ts` regenerated from `services/api/openapi.json`: 0-line diff.

Repros were run with fakes and a temp `COPYCAT_DATA_DIR`. Nothing touched `./data`, `:3000` or `:8787`.

Severity: **blocker** = can lose real money or leave an unmanaged position in normal use today.
**high** = same outcome under a realistic but narrower condition, or a guard that does not hold.
**medium** = wrong behavior or weak guard with bounded impact. **low** = hygiene, docs, defense in depth.

Counts: **blocker 2, high 7, medium 12, low 11**, plus the "silent wrong numbers" section (S1-S12, ranked inline,
some cross-referenced to the findings above).

## Blockers

### B1. A fresh HIP-3 copy on a unified/portfolio-margin account is invisible to our own reads and gets deleted as "vanished" 10 s later
- `services/hl/hl/venue.py:211-229` (`_dexes_to_read`, `_remember_active`), `venue.py:278-324` (`account_state`),
  `services/engine/engine/core.py:1190-1220` (`_reconcile_vanished`), `core.py:1131-1165` (`_resolve_pending`).
- Between full scans (300 s) `account_state` reads only dexes that were "active" at the last full scan: `dex == ""`,
  or `accountValue > 0`, or positions present. Under unified/portfolio margin a HIP-3 dex's `accountValue` is 0
  (collateral sits in spot), so it is never active. On a full-scan cycle `available` has the dex key (unified: spot
  free), so the engine opens `xyz:TSLA`. The next two cycles do not read `xyz`: the copy is missing twice,
  `_reconcile_vanished` deletes the row ("liquidated or closed outside copycat") and ignores the coin. When the
  rescan finds the position it is "not ours": never reduced, never closed, not closed by close-all.
- Repro (fake `http_post`, unified, dexes `["", "xyz"]`): cycle 1 `available {'': 1000, 'xyz': 1000}`; position
  added on `xyz`; cycle 2 and 3 `positions: {}`.
- Same root cause in `_resolve_pending`: a pending open whose cloid status is `filled` but whose coin is missing from
  the read is treated as settled and deleted (`core.py:1161`: "open did not fill (order status filled)").
- Fix: (1) `account_state(user, also_dexes=...)`: the engine passes the dexes of every `copies` row and every coin it
  is about to trade; always read them. (2) After any successful `/exchange` order on dex `d`, append `d` to
  `_active_dexes[account]`. (3) `_resolve_pending`: status `filled` + missing position = vanish-pending, never delete
  on one read. (4) `_reconcile_vanished`: require the second miss to come from a full-scan read. Regression test: the
  repro above through `core.run_cycle` with a unified fake.

### B2. Activating another account mid-cycle sends account A's orders to account B (and close() closes B's position)
- `services/engine/engine/public.py:154-185` resolves `our_address` once per cycle. `services/hl/hl/venue.py:811,862`
  (`sdk.get_exchange()`), `venue.py:904` (`order_status` uses `env.account_address()`), `venue.py:927-941`
  (`close()` sizes from `env.account_address()`), `services/hl/hl/sdk.py:125` re-resolve the ACTIVE account on
  every write.
- Scenario: cycle starts on A (reads A, plans an open of 0.5 ETH for leader L, writes a pending row in
  `engine-A.db`). The user clicks Activate on B (`routes/accounts.py:55` only 409s when A has copies; with no copies,
  or `force=true`, it goes through). The order is signed with B's agent for B. A's db thinks A holds it; B's db has
  no row, so on B it is "not ours" forever. Worse, `close()` for an A copy reads B's size in that coin and
  reduce-only closes B's position (e.g. a close-all or stop running for A while B becomes active).
- Fix: pin credentials per cycle. `run_cycle` captures `(account, agent_key)` once; the venue write methods take
  `account` and refuse (`ok False, error "active account changed"`) when `env.credentials()[0] != account`.
  `close()` and `order_status()` take the account explicitly. Test: switch the vault's active id between the
  pending-row write and `venue.market` in a fake.

## High

### H1. MCP `add_leader` puts money to work without `COPYCAT_MCP_ALLOW_TRADING`, the cap or a confirm code
- `services/mcp/copycat_mcp/server.py:411-422` -> `POST /api/leaders` (`services/api/api/routes/leaders.py`).
- A leader added to the book is copied on the next cycle with the global Settings (default `leverage_mode max`,
  `only_new_positions false`: his current book is entered immediately). With trading live this is a real-money action
  with no per-plan dollar cap, no confirm code and no env flag. A prompt-injected agent (trader name, thesis text) can
  call it. The tool docstring says "this ONLY adds it to the list".
- Fix: remove `add_leader` from the MCP, or route it through the plan/execute path (it is a copy plan with
  `settings_source global`), or have the api refuse `POST /api/leaders` from the MCP token (see H3).

### H2. The confirm code is handed to the model in the same tool result that carries untrusted text
- `server.py:186` (`present_plan` prints `**Confirm code: ...**`), `copy_plan` also returns `latest_thesis.markdown`
  (anyone with the token can write theses, `save_thesis` included) and Scout fields.
- The code is meant to prove the human approved. The model reads it, so a prompt injection in the thesis or a trader
  name can call `execute_copy_plan(plan_id, code)` directly. The only real gate left is the model following
  `EXECUTE_RULE`.
- Fix: never return the code to the MCP. Show it out of band (web UI "MCP plans" panel, or a desktop notification)
  and have the human type it back in the chat. Alternatively require approval in the web UI (`POST
  /api/mcp/plans/{id}/approve`, UI-only token scope) before execute.

### H3. One all-powerful API token, readable by the agent the MCP flag is supposed to contain
- `services/api/api/config.py:56-82` (`data/api_token`), `services/mcp/copycat_mcp/config.py:75-83`.
- The MCP server reads the full token from `data/api_token` (or `.env`). Claude Code, which runs the MCP, has file
  and shell access to the same repo: a prompt-injected session can `cat data/api_token` and `curl -X PATCH
  /api/settings {"enabled":true,"dry_run":false}`, `POST /api/wallets/{a}/copy` with any allocation, or
  `close-all`. `FORBIDDEN_TOOL_WORDS` only limits the tool list, not the credential.
- Fix: a second, scoped token for the MCP (`COPYCAT_MCP_TOKEN`), enforced server-side by a route allowlist (reads,
  thesis PUT, `/api/mcp/plans*`). Keep the full token out of any file under the repo the agent works in (store it
  outside the repo, or in the OS keychain for the web).

### H4. Persisted `contract_version` is echoed back, so an old settings.json makes the web hide v7/v8 terms; "follow his leverage" then trades at MAX leverage
- `contracts/models.py:113` (`contract_version: int = CONTRACT_VERSION` is an input field),
  `services/api/api/settings_store.py:66-72,157,275` (load/patch/copy keep it), `services/web/src/lib/trade/draft.ts:43-45,121`.
- `GET /api/settings` returns whatever `contract_version` was in the file when it was first written. The web derives
  `caps.v7/v8` from it. With a file created before v7, `buildCopyRequest` omits `leverage_mode: "match"`
  (`draft.ts:121`), so a "Follow their leverage" ticket stores no leverage_mode and the engine uses the global one
  (default `max`: coin max up to 50x). With a file created before v8, direction and coin filters cannot be sent.
- Repro: settings.json `{"contract_version": 6, ...}` -> `patch` + `copy_wallet` -> `load().contract_version == 6`
  (code is 9); the wallet's effective `leverage_mode == max`.
- Fix: make `contract_version` server-set (validator that always writes `CONTRACT_VERSION`, ignore the input), and
  have the web read caps from `/api/health` (add `contract_version` there). Check the live file now:
  `jq .contract_version data/settings.json`.

### H5. MCP `$100` cap is a margin cap, not a loss cap: cross margin or match exposure can lose more
- `services/api/api/mcp_plans.py:105-119` (`copy_request_for` sets no `margin_mode`), `mcp_plans.py:393-401`.
- The plan inherits the global `margin_mode`. With `cross`, a $100 allocation at his 40x (exposure match, leverage
  match) is about $4,000 notional drawing on the whole account's margin; a liquidation costs far more than $100.
  `check_caps` checks only `amount_usd` and the user-supplied `leverage`. There is also no cumulative cap: 10
  executes/hour on 10 wallets is $1,000/hour.
- Fix: force `margin_mode=isolated` on MCP plans; cap planned notional (`preview.planned_notional_usd <= amount x
  max_lev_for_mcp`); add a rolling cap on total MCP allocation (sum of MCP-created allocations in the book).

### H6. Deleting the active account leaves its copies unmanaged with no guard
- `services/api/api/routes/accounts.py:75-78` vs `activate` at `:55-66`.
- `activate` refuses (409) while the current account holds copies; `DELETE /api/accounts/{active}` does not. The
  engine goes idle ("no active trading account") and every open copy, leveraged and isolated, stops following exits.
- Fix: same 409 check as `activate` (positions from `engine_status(address)`), `force=true` to override, and a
  confirmation in the web.

### H7. Switching accounts copies every wallet's whole current book onto the new account immediately
- `services/engine/engine/core.py:338-352` (no leader state in the new db -> no baseline unless
  `only_new_positions`), `docs/ARCHITECTURE.md` "Switching accounts gives the new one a clean engine book".
- The book (`settings.json`) is shared across accounts. On B's first cycle every leader has no `LeaderState`, so
  with trading live and `only_new_positions` false, every position each leader holds is entered on B at the current
  price (gated only by `max_worse_entry_pct`, default 10%). Nothing in the activate flow says this.
- Fix: on an account switch (`switch.note_account` returns prev), baseline every leader for that account (treat the
  first cycle as `only_new_positions`), or require `enabled=false` to activate, with an explicit "copy current books
  on B" opt-in.

## Medium

### M1. The api's HL reads run at "engine" priority when `hl` was imported via the vault first
- `services/hl/hl/rate_limit.py:162,320-332` (limiter built at import), `services/api/api/accounts_backend.py:31`,
  `engine_client.py:105,124`, `market_client.py:36` (set the env var only; no `set_priority`).
- `GET /api/accounts` imports `hl` through `vault.hlops` at engine priority. Setting
  `os.environ["COPYCAT_HL_PRIORITY"]="background"` afterwards changes nothing. Repro: after `hlops._acc()` then
  `AccountsBackend()._venue()`: env `background`, `HL_LIMITER.priority == "engine"`, `_reserve == 0.0`. A preview of
  a 60-coin wallet (MCP plan, ~40 s of reads) can then drain the 40% reserve and make the engine's own account read
  fail ("our account read failed": no exits that cycle). Fixed only after the first Scout call (`set_priority`).
- Fix: `rate_limit.set_priority("background")` in `create_app()`; replace the env writes with `set_priority`.

### M2. An open rejected for a transient reason is ignored until the leader goes flat
- `core.py:1015-1021`. HTTP 429 (SDK `ClientError`, not in `_AMBIGUOUS_EXC`) or "slippage cap" returns
  `ok False, ambiguous False`: the pending row is deleted and the coin is added to `ignored`. That position is never
  copied, with one skip event.
- Fix: classify rejections: 429 / slippage cap / "insufficient margin" -> `retry` (freeze prev, re-check worse-entry
  next cycle); only permanent rejections ignore.

### M3. Unknown ledger row type disables the daily loss halt for the rest of the UTC day
- `services/engine/engine/daypnl.py:97-98`, `core.py:1513-1518`.
- One row of a type not in the table (`rewardsClaim`, borrow/lend, any new HL type) since the anchor makes every cycle
  unreliable until the anchor rolls; an unhalted account then never halts that day, however much it loses. Today a
  real loss and a failing ledger read look the same.
- Fix: treat an unknown type as 0 when it has no USDC field and as unreliable only inside the ambiguity window; log
  the type once; add a gate test per known HL type.

### M4. Stop flag re-issued mid-cycle is deleted by the engine
- `services/engine/engine/public.py:186-187` (`_clear_stop` unlinks by name after the cycle).
- `stop(close_positions=false)` is read at cycle start and finished; the user then posts `stop(close_positions=true)`
  before the cycle ends; `_clear_stop` deletes the new flag. Copies follow his exits instead of closing.
- Fix: carry `requested_ms` in `read_stops()` and delete only when the file's `requested_ms` still matches.

### M5. `one_shot` is invisible in the web and survives a Trade-ticket re-post
- `services/web/src/lib/trade/types.ts:103-135` (no `one_shot`), `draft.ts:113-131` (never sends it),
  `settings_store.py:256-266` (custom keeps previous override fields).
- An MCP plan with `follow=false` makes the wallet one-shot. The Trade page shows it "running" like any wallet;
  adjusting it in the ticket keeps it one-shot, so new positions are silently never copied.
- Fix: add `one_shot` to the hand type, show a badge, and have the ticket send `one_shot: false` on an explicit
  "follow" save.

### M6. Passphrase guessing budget is 5x the documented one and resets on restart
- `services/api/api/attempt_limit.py:15-36`; buckets `refresh`, `transfer`, `action-usd_send`, `action-withdraw`,
  `action-usd_class_transfer` each allow 30/h: 150 passphrase checks/hour, in memory.
- Fix: one shared `passphrase` bucket for every route that unlocks the main key, persisted (e.g. a small file under
  `data/vault/`), with exponential backoff per account.

### M7. scrypt N=2^15 for keys that can withdraw
- `services/vault/vault/crypto.py:30`. ~32 MB / ~50 ms per guess; an offline attacker with a copy of
  `data/vault/keys/*.main.json` tests fast. Blobs carry their params, so raising it is backward compatible.
- Fix: N=2^17 (or 2^18), r=8, p=1 for new blobs; re-seal on the next successful unlock.

### M8. Stopped wallets lose per-wallet terms that matter for exits
- `settings_store.py:312-328` drops the override; `core.py` then uses global `for_leader(addr)` for orphans.
  `max_slippage_pct` is global anyway, but a stopped one-shot/counter wallet's catch-up and ledger terms are only kept
  for allocation wallets (`core.py` `_fill_wallet_fields`). Exits themselves are direction-safe (sign of our
  position), verified.
- Fix: keep a frozen copy of the override in the ledger row (`terms`) for every wallet, not only allocation ones.

### M9. `_resolve_pending` and pending reduces trust one read for "flat"
- `core.py:1172-1185`: a degraded read (see B1) gives `size_after = 0`, books the whole order as filled with the
  mid at resolution time, then the copy vanishes. Covered by the B1 fix; listed so the regression test covers the
  reduce path too.

### M10. Events of every account share one `events.jsonl`
- `engine/public.py:74-75`, `api/routes/wallets.py` `wallet_events`. After a switch, a wallet's history mixes
  account A and B fills; `_log_skip_changes` state is per db but the feed is not.
- Fix: add `account` to `EngineEvent` (contract bump) and filter by the active account in the api.

### M11. `remove()` deletes a connected account's agent key without a check that trading still needs it
- `services/vault/vault/manage.py:72-87`. Same hazard as H6 from the vault side; fix together.

### M12. No code-version handshake between api, engine and scout processes
- `services/api/api/routes/health.py:16` returns the constant `API_VERSION = "0.1.0"`; `EngineStatus` carries no
  version. The api imports `engine.sizing` / discovery code at its own start, so after a pull the api's preview,
  what-if and MCP plans run old code while the engine runs new code (the stale-process what-if that showed
  liquidations at 1x is this class).
- Fix: each process writes `{git_sha, started_ms}` (engine in `engine_status.json`, scout in its status); the api
  compares with its own and the web shows "restart api" when they differ.

## Low

- **L1.** `docs/ARCHITECTURE.md` says MCP plans live 120 s; code is `MCP_PLAN_TTL_S = 300`
  (`contracts/models.py`). The WIP in `server.py` fixes the MCP side only.
- **L2.** Docker: the api container gets no `COPYCAT_MCP_ALLOW_TRADING` (explicit env list in `docker-compose.yml`),
  so `ENABLE_HINT`'s "(or .env)" is wrong under compose. Fails closed.
- **L3.** `usd_send` "only to another vault account" (`vault/funding.py:87-93`) is cosmetic: `withdraw` to any address
  is allowed with `confirm_destination`, and a token holder can import any address they control as a vault account.
  Document it as a typo guard, not a security boundary.
- **L4.** `machine.key` lives in `data/vault/` next to the agent blobs (`crypto.py:45-52`): read access to `data/` =
  agent keys (trade, not withdraw). Documented threat model; consider the OS keychain.
- **L5.** `read_agent_key` binds AAD to the address stored in the blob itself (`store.py:112-117`), not to the
  row's `agent_address`. Caught by `active_credentials`' derived-address check (`manage.py:135`), so not exploitable;
  pass the row's address for consistency.
- **L6.** `archive_main_key` uses `Path.replace` with no fsync of `removed/` (`store.py:137-142`).
- **L7.** Deposit bridge/USDC addresses come only from the api (`depositFlow.ts:95,149`); pin them in the web too.
- **L8.** `COPYCAT_HL_BASE_URL` loopback override (WIP `hl/env.py`): mainnet-signed actions go to whatever listens on
  localhost. Gate it behind `COPYCAT_E2E=1` as well.
- **L9.** `dry_run` blocks exits of REAL copies (`core.py:478-487`, by design): flipping live -> dry run leaves
  leveraged positions unmanaged. The UI should warn when dry run is turned on with copies open.
- **L10.** close-all and stop act on the active account only; copies left on an inactive account (forced switch) can
  only be closed by re-activating it. Say so in the close-all confirm dialog.
- **L11.** Demo `preview` labels its local estimate `source: "api"` (`lib/trade/source.ts:253-260`). Demo only.

## Verified OK

Vault / accounts
- AES-256-GCM everywhere, 12-byte random nonces, AAD `copycat/vault/v1/{id}/{purpose}/{address}`; scrypt params
  bounded on read (no RAM bomb from a tampered blob); `WrongPassphrase` is one message for every auth failure.
- Files 0600 via `mkstemp` + `fchmod`, dir 0700, atomic replace + dir fsync, vault mutations under flock, modes
  re-tightened on read; machine key created with `link()` so racing processes end with one key.
- Remove archives the created wallet's main key to `vault/removed/` (never deleted).
- approveAgent: exact key set, `hyperliquidChain` pinned, nonce equal and within 15 min, agentName regex, canonical
  action rebuilt server-side, signer recovered and compared to the main address, agent != main.
- usdClassTransfer / usdSend / withdraw3: exact key set per kind, type/chain pinned, nonce within 10 min, amount
  regex + `amount_str` round-trip, guards re-checked at submit with live limits, canonical action rebuilt, signer ==
  account address; the SDK's own field lists so browser and server hashes match. HL nonce dedupe stops replay.
- Main-key guard on every entry path (`import_api_key`, `submit_agent_approval`, `.env` via `sdk.check_agent_key`),
  and `active_credentials` re-derives the agent address.
- No key, passphrase, signature or typed data in any logger call on these paths (every call listed and read);
  `/api/accounts*` 422s are scrubbed; vault audit log rejects unknown fields.
- Import-env reads `.env` at request time, refuses a main key, never leaves the key in the api env.
- Auth on every route but health, constant-time compare, token >= 32 chars, `change-me` refused;
  TrustedHostMiddleware (localhost/127.0.0.1); CORS single origin, no credentials; compose publishes on 127.0.0.1.
- `sdk.get_exchange` keys the cached Exchange on (agent, account, url): no stale Exchange after a switch (B2 is about
  the cycle, not the cache).

Engine
- Pending-row protocol: row before the order, cloid, 30 s grace on `unknown`, no blind re-send of an ambiguous open,
  add or catch-up; ambiguous reduces parked and re-derived from our real size; partial reduce `_retry_prev` math.
- Fixed-size cap on adds and catch-ups, allocation cap with slack, bump only from >= 25% of the floor, margin room
  check after bump, liquidity split with carry dropped under the minimum, $50k uncapped fallback.
- Coin filters and pause gate entries and catch-ups only; exits never filtered. One-shot snapshot keyed by
  `invested_ms`, pruned on close/flip.
- Leverage capped by coin max and `max_position_leverage` in every mode; target exposure uses the capped leverage.
- Close-all and stop close reduce-only even in dry run, keep the flag until flat; archive refuses while any real or
  shadow copy exists.
- One worker per data dir (flock); settings last-good copy per db; per-leader and per-coin exception isolation.
- Day PnL nets deposits, withdrawals, sends, vault flows; ambiguity window; halt holds its state on unreliable reads.

MCP
- `execute_copy_plan` registered only with the flag in the MCP env, refused by the api without it in the api env;
  single use under flock, TTL, 3 bad codes burn the plan, constant-time compare, book fingerprint over planned coins,
  book room, 10/hour, every attempt audited with no code or token. Execute never touches `enabled` / `dry_run`.
- Thesis markdown is rendered with `react-markdown` without raw HTML (`SafeMarkdown.tsx`).

Wiring
- `openapi.json` matches the app (gate test) and `schema.gen.ts` matches `openapi.json` (regenerated, 0 diff).
- Web demo guard: every write goes through `apiFetch`, which throws on `?demo=1`; no raw `fetch` elsewhere; legacy
  route redirects keep the query string (demo survives).
- `settings.json` single writer with flock + atomic replace; `mcp_plans.json` 0600 + flock; flags written atomically.
- SSE passes engine lines through unchanged; the web uses `fetchEventSource` with the bearer header.
- The Settings-tab override editor starts from the full stored override, so saving it keeps `invested_ms`, `paused`,
  `one_shot` and v8 fields.
